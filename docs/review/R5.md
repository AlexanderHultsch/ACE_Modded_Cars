## Value questions

### pbedit versus main's car_json
- pbedit needs no `schemas/`; car_json needs `schemas/acevo.desc` (vendor data, only on the PC). Only pbedit can run in the cloud on a real car file.
- car_json is the owner-approved edit path (names, enums, `_order/_packed/_unknown`, rejects what it cannot reproduce). pbedit addresses by field number only (`39.1`, `10[2].2`); there are no names, enums, `[key=VALUE]` selectors, `[*]` wildcards or create-missing, which main's catalogue relies on. So pbedit cannot replace car_json in the tuner.
- Real extras: independent oracle (a second parser for differential tests of car_json, pb_raw and extract_protos, which R1-017 lists as three copies of the same loop), schema-free inspection, handling of the types car_json leaves unmapped, in-place patching that keeps untouched bytes (NaN payloads, overlong varints; car_json loses NaN sign/payload, R2-003), `str` edits that recompute lengths (the rename of a car id to another length would need it).
- Cost: a 4th wire parser in the tree and a second editing path that CLAUDE.md of the branch calls THE edit path ("only through pbedit/tune"), against main's owner decision (car_json). Hence PORT-ADAPTED as a diagnostic/oracle with the docstring line above, decision to Alex.

### refgraph
Main has no cross-reference check. `refgraph <root>` on `<work>\<car>\build\<new_id>` would flag any `content\cars\<new_id>\...` string whose file does not exist: the failure class of the same-length-id clone (renamed files, tyre files repointed by build_tyre, R3-003) that today surfaces only in the game. Verified here on the third-party E46 (157 files, 0 MISSING, 0.28 s) and on a synthetic tree (ok / MISSING / external / fallback, exit 1). It does not need the game, only the extracted/built tree, so it is cloud-testable on synthetic input and PC-usable on real builds.

## Prototype (the proof that the approach works)
`S/review/work/r5proto/tests/test_kspkg.py` (107 lines) imports a COPY of MAIN's tools (`S/review/work/r5proto/tools`, byte copies of MAIN/tools/*.py). Run: `cd S/review/work && python3 -B -m unittest discover -s r5proto/tests -v`:
```

test_pack_entry_names_use_backslashes ... expected failure      # R1-007 (posix only)
test_pack_then_extract_roundtrip ... ok
test_truncated_entry_is_an_error ... expected failure           # R1-005
test_verify_same_package_is_identical ... ok
test_path_hash_empty_is_fnv_offset_basis ... ok
test_xor_is_an_involution ... ok
Ran 7 tests in 1.560s   OK (expected failures=2)
```
What it contains: a package builder written from the format constants, independent of `cmd_pack` (1 MiB header, XOR-flagged data, 64 MiB XOR'd table), so list/extract/verify are tested without trusting pack; a pack -> extract round trip; the two characterization tests.
Checks I ran so the expected failures are not "failing for the wrong reason":
- Decorators stripped, MAIN modules: `FAILED (failures=2)`: `AssertionError: ValueError not raised` (R1-005) and `AssertionError: Lists differ: ['/content/cars/abc/data\\a.txt', ...] != ['content\\cars\\abc', ...]` (R1-007).
- Decorators stripped, MAIN kspkg with only the R1-007 fix (`os.sep`): the R1-007 test passes, the R1-005 test still fails with `ValueError not raised`, i.e. each fix flips exactly its own test (S/review/work/r5proto/strip2).
- Lesson recorded by the prototype: a pack -> extract round trip passes even with the R1-007 bug, because `safe_path` accepts both separators (extract hides the mangled names). The assertion that finds it reads the table (`kspkg.read_table`) and compares entry names. A round trip alone would have given false confidence.
How to express an expected failure with Python 3.9 unittest: `@unittest.expectedFailure` on the test method (or class). It reports "expected failure" and keeps the run green; when the bug is fixed the test turns into "unexpected success", which makes `wasSuccessful()` False (since 3.4), so the fix commit must delete the decorator: the suite itself prompts the clean-up. Platform-conditional xfail: `XFAIL_POSIX = unittest.expectedFailure if os.name != "nt" else (lambda f: f)` (used in the prototype). Do not combine `expectedFailure` with `self.subTest` (unreliable result reporting in 3.9; use one assertion or loop outside subTest in xfail tests). Put the finding ID in a comment next to the decorator. Before committing an xfail run it once with the decorator removed and read the failure message (done above).

### Rules for the suite
- Characterization first: every R1..R4 finding that is a behaviour change gets an `expectedFailure` test that fails today for the intended reason (verified by stripping the decorator once); the fix commit deletes the decorator. Findings that are comment/T1 changes get no test (except doc count tests).
- Time-based assertions are avoided (flaky); performance findings are protected by counts (opens per request, parse calls, reads per file), not seconds.
- One 65 MiB package per class (setUpClass) keeps test_kspkg.py under about 4 s; the whole suite is estimated at 15-20 s.
- The 17 branch tests that need the third-party mod's data are not ported; their logic is rebuilt on a synthetic car tree (R5-A-023).
